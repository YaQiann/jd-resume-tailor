# 按 JD 定制简历

## 首稿检查

- 精简前核对每个动作、案例和数字分别支撑哪项 JD 要求。对照现稿与改稿，优先压缩重复措辞和次要细节。若某素材为核心要求提供独有证据，或补充了不同的相关能力与成果，尽量用短句保留。删减后重查岗位要求是否仍有证据，同条里的案例、决策和数据各归原项目，归属未确认时分开表述。

- 将优先岗位要求对应到具体项目、本人动作与结果证据。发现条目只能靠新增关键词体现匹配时，回到项目素材，把相关动作融入原经历。
- 先判定项目边界，再分配篇幅。共享业务目标、交付物或上下游关系的动作，写成同一条经历。即使策划、制作协调、审核和发布分别对应 JD 中的不同要求，也按它们在同一次内容交付中的关系组织。一项工作有独立目标、交付物或可归属成果时，再考虑单列。两个案例合写时，优先各留一项代表性成果，保留必要的时间、范围及归因。
- 中文投递版按招聘场景改写标题和正文。词义吃不准时，对照同地区、同职能的公开 JD。用岗位术语描述已确认的职责，例如根据 CTR、CPC 调整素材可写「媒介投放与优化」。术语下要有具体动作。

1. **定位素材。** 读取 JD、用户指定的基准简历、完整经历库及对话中后来确认的补充材料。优先查工作区的 master/profile 文件。可读取工作区已有的 `resume-master.md` 或 `career-profile.md`，并用用户确认的补充材料更新事实。用户最新确认的事实和撤回决定优先于旧稿。发生数字、日期或职责冲突时，采用可核实口径或暂时省略冲突细节。
2. **先做证据匹配，再写。** 按 JD 的核心职责、硬性要求和加分项排序。逐项找同公司同项目的证据，区分直接匹配、部分可迁移和缺证据。对照完整经历库决定新增、保留、替换或精简哪些项目。保持完整任职时间线。早期项目能证明核心要求时保留足够细节。岗位术语只有在语义与本人职责吻合时才采用。
3. **用范例补证。** 关键要求只有部分证据时，先指出最接近的真实项目，再给一个标为「参考范例，待确认」的典型做法和可观测结果，最后问一个具体问题，例如「官网建设时，页面标题和描述是你制定、审核，还是由供应商负责？」可说明不同回答对应的简历措辞。对陌生行业做法可查可信资料。示例、行业惯例、公开网站现状只用于提示和核对，不写成用户的历史职责或成果。缺证据也可先完成其余部分。
4. **按项目重写。** 将同一项目的背景、本人动作、交付及有依据的结果写进原条目，交代动作间的关系，避免在旧句末尾补关键词。独立项目有清晰的责任或成果时可独立成条。例如，把栏目规划、页面标题与描述、H1–H3 和站外引流融入同一官网项目。GEO 项目可单列，注明指标的监测范围。达人和广告投放按 JD 的相关度择取，结果各归原项目。没有量化数据时，可写已确认的上线或交付，避免把现时可见性写成历史排名提升。
5. **定稿与交付。** 采用目标市场自然的招聘用语，沿用用户已确认的职称、数字口径及版式偏好。每个 JD 独立保存一份定稿正文，HTML 和所需 PDF 由该定稿生成，已有基准简历和其他岗位版本保留。检查重点条目的岗位映射、证据、事实口径，以及导出文本、分页和页眉页脚。交付时简短说明换入或前移了什么、压缩了什么，以及仍缺哪项重要证据。

## 讨论关键缺口与匹配度

- 首轮定制时，主动向用户汇总 JD 的关键职责与硬性门槛，逐项说明直接匹配、可迁移、待确认或确认无经验，并指出具体证据和剩余差距。检查完整任职经历，交代哪些早期项目值得保留或压缩及其理由。首轮呈现完整判断，后续按影响大小一次追问一个关键问题。

- 收到补充经历后，先向用户说明它对目标 JD 的实际增益：原先缺哪项证据，这段经历能让该要求变成直接匹配、部分匹配，还是几乎没有变化。给出具体依据和剩余差距，再建议单列、合并、追问或省略，最后才修改简历。

- 用户补充事实后，先做编辑判断，再更新简历。明确它对应哪项 JD 要求、能证明什么、还有什么差距，以及是否比现有证据更值得占用篇幅。确认做过只解决真实性，选材还要看相关性、本人贡献和证据强度。
- 主动给出取舍及理由。证据强就建议保留或替换弱条目；同一项目的补充细节能说明关键动作时融入原条目；常规协助或弱相关素材省略。跨职责的推断需要独立证据。
- 关键素材过于笼统时，先提出一个具体的改写方向和一个最值得补充的问题（如合作阶段、本人决策或可核实结果），再根据答案决定写法。说明取舍后继续完成已有证据支持的部分。

- 对照 JD，把关键要求标成「有直接证据」「有可迁移证据」「待确认」或「确认无经验」。指出具体缺在哪一步，例如海外账号独立运营与国内社媒内容运营之间的差距。
- 对缺少直接证据的关键业务，先查完整经历库。依据业务目标、工作方法、个人职责或交付物判断是否可迁移，关键词相同不足以判定。
- 找到真实线索时，指出具体项目、可迁移的方法和与目标业务的差距，给一句基于现有事实的简历写法，再问用户是否有某个具体动作或结果可补。根据确认的内容更新表述及匹配判断。
- 找不到合理线索时，只问一次是否有未记录的相关经历。用户确认没有，就标记该项缺口，结束这项讨论并继续交付。
- 缺口讨论结束并更新简历后，主动交付「JD 与最终简历匹配度：约 X%」。按 JD 预先划分硬性门槛、核心职责与加分项并分配权重，总权重为 100%。以最终简历中的确认事实评分：直接匹配计满、可迁移按覆盖程度计部分、缺证据或未确认计零。简述主要得分点、扣分项与仍未满足的硬性门槛，并说明这是岗位匹配估算。若用户继续补充或修改简历，重新核算。

## 后续修改与导出

在该岗位定稿的源文件中记录已确认的用语、项目拆合、删减和导出偏好。局部改动和撤回只应用于目标字段，按差异检查其余正文。下载时以最新定稿重导，并检查 PDF 可提取文本、姓名和职位、分页、裁切及是否带出浏览器页眉页脚、模板文字或本地路径。沿用已确认的版式，检查通过再交付下载文件。

## 用真实案例验收

- 定制首稿：同项目的动作按实际流程合并，成果归属明确，支撑不同核心要求的证据在压缩后仍可辨认。
- 定稿后只改某家公司的职位：对照正文确认只有指定职位有变化。若要求下载，检查 PDF 和 HTML 职位一致，并核对分页与附加文字。
